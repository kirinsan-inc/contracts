# 株式会社kirinsan 標準契約書

株式会社kirinsanの標準契約書と改定履歴を公開するためのリポジトリです。

公開先：**[kirinsan-inc/contracts](https://github.com/kirinsan-inc/contracts)**

目的は、パートナーの皆さまが契約の内容と更新箇所を確認できるようにすることです。標準雛形、補足説明、改定履歴、およびこれらからPDFを生成するためのファイルを管理します。

> **公開されている最新版が、既存の締結済み契約を自動的に変更することはありません。**
> 各当事者間には、締結時またはその後の変更合意で特定した版・条件が適用されます。契約期間を同一条件で更新しても、適用版は自動的に変わりません。新版を適用するときは、対象の版と適用開始日を明示して、再締結その他の記録に残る方法で合意します。

## 公開するもの・保管しないもの

公開するのは、記入前の標準雛形、対応する説明資料、版固定ファイル、改定履歴、および公開資料のみを処理するPDF生成設定です。

次のものは、このリポジトリの外にある非公開の保管先で管理します。

- 締結用に情報を記入した文書、署名済み契約、電子署名・締結記録、相手方の住所・連絡先等
- 実際の発注書、報酬額、工数、作業期間、担当者、クライアント名および具体的な取引情報
- クライアント契約、個別の知財条件・追加条件、その通知・承諾記録
- アクセス先、認証情報、案件のソースコード、テストバイナリおよび内部資料
- 案件ごとのAI利用条件、許可ツール・設定、申請・承認記録

これらは一時的な作業ファイルとしても本リポジトリ内に置かず、Git履歴、Issue、Pull Request、CIログや成果物にも含めません。公開後にファイルを削除しても、履歴や取得済みの複製から消えるとは限りません。

## 契約と版の使い方

1. **共通ルールを締結する。** 業務委託基本契約とNDAをそれぞれ締結し、文書番号・適用版を記録します。標準雛形から生成したPDFに必要な記入欄・署名欄を付け、Google Workspaceの電子署名機能で乙の承諾を得ます。個人パートナーを標準にした締結欄があり、法人の場合の欄も用意しています。甲が版を特定した契約書を提示し、乙が署名して承諾する方式では、甲の署名を必須としません。締結用の本文、乙の承諾、締結日及び電子署名の完了記録・監査証跡を非公開で保管します。
2. **NDAと情報管理を先に整える。** 秘密情報の開示・アクセス許可の前にNDAを締結します。NDAに組み込む情報セキュリティ遵守事項も版を特定して提供します。秘密保持・情報管理に関する抵触はNDAを優先します。
3. **案件ごとに非公開で発注する。** 準委任・請負の区分、業務、期日、報酬、支払日、検査、権利処理等を、発注時に法令に従って書面または電磁的方法で直接明示し、着手前に合意します。単に本リポジトリを公開するだけでは個別条件の明示・契約成立を代替しません。
4. **特殊な知財条件は案件ごとに合意する。** クライアントへの権利移転や留保資産の著作者人格権不行使等は、対象・範囲・対価等を事前通知し、必要な合意を非公開で記録します。著作者人格権を譲渡するという扱いはしません。
5. **一般契約は継続して使用する。** 基本契約とNDAはそれぞれ定めた期間・同一条件で継続します。案件終了や標準様式の更新ごとに、当然に巻き直す運用ではありません。NDAの継続は、作業・テスト期間やアクセス許可の延長を意味しません。
6. **改訂を適用するときだけ変更合意をする。** 合意した版、適用開始日、本文および合意記録を非公開で保存します。締結時の識別には、移動する`latest.md`だけではなく、版固定ファイルと必要に応じコミットID・タグを用います。

相談窓口、事故連絡先、アクセスの対象・範囲・期間等は、公開雛形へ案件情報を書き込まず、非公開の案内・記録で具体化します。AIツールの利用可否、対象情報及び申請方法も、案件ごとに別途案内します。

## 改訂の手順

1. 改訂本文を新しい日付の版固定ファイルとして作成します。同日の再改訂は`2026-10-05-r2`等、識別できる別の版とします。公開済みの過去版は上書きしません。
2. 対応する`CHANGELOG.md`に変更理由・対象条項・既存契約への影響を記録し、補足説明も同じ本文版に合わせて更新します。説明だけを改訂する場合も、説明資料に独自の改訂識別子を付けて履歴を残します。
3. `latest.md`を最新の版固定本文の完全なコピーにし、`guide.md`も説明の版固定ファイルと一致させます。READMEとPDF生成対象を更新します。
4. 文書間の参照、本文と説明の整合、公開範囲、PDFの見た目と文字欠けを確認します。
5. 公開と個別の変更合意を分けて進めます。リポジトリの公開・更新通知だけで既存契約を変更しません。

## PDF

Markdownを原本として、**GitHub Actionsで**本文3点、AIツール利用ガイドライン1点、補足説明2点のPDFを生成します。PDFは派生成果物として扱い、本文と別々に編集しません。表題、版、見出し、余白、ページ番号、日本語フォントおよび締結欄を共通の印刷設計で整えます。

初回公開後、対象ファイルの更新や手動実行で生成・検証し、Actionsの実行結果からPDF一式を取得します。成果物の保存期間は30日です。署名に使うPDFは、取得後に必要な記入欄・署名欄を加えて非公開で保管します。生成PDFの自動コミットやReleaseへの自動掲載は行いません。詳しくは[PDF生成の説明](print/README.md)を参照してください。

支払は、乙からの給付の受領または役務の提供を基準とし、クライアント側で評価完了までを「納品」と呼ぶ場合も、その呼称や入金確認だけで受領日・支払期日を後ろ倒ししない設計です。コードの途中提出と最終の受領、評価対応の作業範囲・期間・対価は案件ごとに事前に区別します。本案では原則翌月末払いに加えて実日数60日以内への繰上げを契約条件として採用しています。行政上の月単位の計算方法を否定したり、翌月末払い自体を一律に違法とする趣旨ではありません。
